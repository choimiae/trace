# 요소 신원 설계 — 형제 요소를 구분하는 지문과 서버측 동일성 판정

## 배경

탐지기는 "사용자가 같은 것을 반복해서 눌렀나" 를 요소 지문(`elementSelectorHash`)의 동일성으로 판단한다. 그 지문을 만드는 `buildSelector`(`packages/sdk/src/dom.ts`)는 `태그 + #id + [role]` 세 조각만 쓴다. 그래서 id 도 role 도 없는 `<button>` 은 전부 선택자 문자열이 `"button"` 이 되어 같은 해시를 갖는다.

실제 브라우저 수집으로 확인한 결과(2026-09-03, 화면 맥락 2단계 Task 8 검증):

| 누른 버튼 | id | 선택자 | 해시 |
|---|---|---|---|
| 권한 추가 | `dead-click` | `button#dead-click` | `616730d0` |
| 저장 | 없음 | `button` | `ade22732` |
| 리포트 내보내기 | 없음 | `button` | `ade22732` |
| 오류 발생 | 없음 | `button` | `ade22732` |

결과로 **일어나지 않은 분노 클릭 이슈가 생성됐다.** 이슈 `issue__|ade22732|rage_click` 은 "4회 클릭이 3초 안에 같은 요소에서 발생했습니다" 라고 보고하지만, 실제로는 서로 다른 버튼 3개를 각각 1·1·2회 누른 것이다(00:19:23.921 저장 / 24.431 리포트 / 24.488·24.548 오류). 반대 방향으로는 서로 다른 버튼의 진짜 문제가 한 이슈로 병합된다.

id 없는 버튼은 웹에서 예외가 아니라 기본값이므로 엣지 케이스가 아니다. 이 결함이 지금까지 안 걸린 이유는 이전 검증이 모두 해시를 손으로 다르게 넣은 시드 데이터였기 때문이다.

## 목표

- 서로 다른 컨트롤이 서로 다른 요소로 인식된다. 허위 분노 클릭·반응 없는 클릭 이슈를 만들지 않는다.
- 같은 역할의 컨트롤이 반복되면(목록 행마다 있는 `삭제`) 하나의 요소로 유지된다.
- 과거에 쌓인 옛 규칙 지문이 틀린 이슈를 영구히 재생성하지 않는다.

## 목표가 아닌 것

- **위치 기반 구분.** `nth-of-type` 체인으로 목록 행을 갈라내지 않는다. 행 3 의 삭제와 행 5 의 삭제는 같은 이슈여야 한다("삭제 버튼이 먹힌다" 는 한 건의 보고). DOM 순서가 바뀌면 같은 버튼이 다른 요소로 보이는 불안정성도 피한다.
- **`aria-label` 과 클래스 사용.** `aria-label` 은 행마다 다른 라벨(`김철수 삭제`)이 붙어 위 동일성 기준을 깨고, 그 문자열의 지문을 남기는 것은 텍스트 정책에 어긋난다. 클래스는 CSS 모듈·빌드 해시로 배포마다 바뀐다.
- **대표 이벤트를 이슈 단위로 고르는 문제.** `findRepresentativeEvent`(`apps/api/src/routes/admin-proxy.ts`)가 세션 단위로 고르는 별개 결함이다. 별도 작업 — 아래에 조사 결과를 남겨 다음 작업이 처음부터 다시 파지 않게 한다 (2026-09-03 확인).
  - 후보 선별 조건이 `projectId` · `sessionIds`(최대 3) · `urlPath` · 시간창 · 이벤트 타입 다섯 개뿐이고 **요소 신원이 없다.** 그래서 한 세션에서 나온 이슈들이 같은 클릭을 근거로 쓴다.
  - 시간창이 `firstSeenAt − REPRESENTATIVE_LEAD_IN_MS(30초)` 부터라 **이슈 자신보다 앞선 이벤트도 후보에 든다.** 2단계 실측 사례: `권한 추가` 8회 반복 클릭 이슈의 근거 표가 58ms 앞선 `저장` 클릭을 표시했다.
  - `error_friction` 에서는 **구조적으로 항상 틀린다** — 오류 이벤트에는 `screenContext` 가 없어 선택되는 것은 언제나 어떤 클릭이다.
  - 사용자-facing 피해는 2단계에서 근거 표의 라벨을 `클릭` → `화면 내 클릭` 으로 낮춰 **거짓 진술은 막혀 있다**. 남은 것은 근거의 질 저하다.
  - 고치려면 `Issue` 계약에 요소 키 필드가 필요하다. 지금 계약에는 없고, 이슈 id 안에는 들어 있으나 **id 를 파싱하는 코드는 저장소 전체에 0건**이며 그 성질은 유지할 가치가 있다(최종 리뷰 지적). §2 의 `elementKey` 를 그대로 재사용할 수 있다.
  - 범위: 공유 계약 · 탐지기 `makeIssue` · SQLite 스키마+마이그레이션+매핑+upsert arity · MemoryStore · `ScreenContextEventQuery` 와 양쪽 스토어의 `findScreenContextEvents` · enrichment · 테스트. 온전한 태스크 하나.
  - 값싼 부분 개선 하나: `REPRESENTATIVE_LEAD_IN_MS` 를 없애면 이슈 시간창 밖 이벤트가 선택되는 것은 막힌다. 창 **안**에 다른 요소의 클릭이 있으면 여전히 틀리므로 부분적이라는 것을 알고 써야 한다.
- **`upsertIssues` 의 일반적인 생존 이슈 정리.** 삭제 경로가 없어 낡은 이슈 행이 영구히 남는 문제는 이 설계의 일회성 마이그레이션 범위를 넘는다. 별도 작업.
- **오류 이벤트의 요소 신원.** 오류 이벤트는 요소 메타데이터를 싣지 않으므로 이슈 키가 `page` 다. 이 설계는 그 동작을 그대로 유지한다.

## 1. 지문 규칙 (SDK)

`buildSelector` 가 만드는 문자열에 개발자가 쓴 값만 추가한다. 사용자 텍스트는 넣지 않는다.

```
현재:  button
변경:  main>form>button[type="submit"]      ← 저장
       main>div>button                      ← 리포트 내보내기 / 오류 발생
```

### 조각과 순서

선택자 문자열은 다음을 이 순서로 이어 붙인다.

1. **조상 태그 체인** — `parentElement` 를 따라 위로 최대 3단, 태그 이름만, `>` 로 연결. `documentElement` 에 닿으면 멈춘다. 클래스·id·속성은 조상에서 읽지 않는다.
2. **자기 태그 이름** (소문자)
3. **`#id`** — 단, **`:` 를 포함한 id 는 건너뛴다.** React `useId` 가 `:r1:` 형태를 렌더마다 새로 만들어, 현재 규칙에서는 같은 버튼이 렌더마다 다른 요소로 갈린다(기존 결함, 함께 닫는다). `:` 없는 다른 생성기(예: 무작위 UUID id)는 이 가드가 잡지 못한다 — 알려진 한계로 기록한다.
4. **안정 속성** — 존재하는 것만, 이 고정 순서로: `data-trace-id`, `data-testid`, `name`, `type`. `[속성="값"]` 형태. 값은 64자로 절단한다(비정상적으로 긴 속성값이 선택자 문자열을 키우는 것을 막는다).
5. **`[role="..."]`** — 현재와 동일.

순서를 고정하는 이유: 같은 요소가 항상 같은 문자열을 만들어야 해시가 안정적이다.

### 해시 폭

`hashSelector` 를 32비트에서 **64비트**로 넓힌다. 선택자 문자열이 다양해지면 서로 다른 요소가 같은 해시로 충돌할 확률이 오르고, 그 충돌은 지금 고치는 버그와 증상이 동일하다. 32비트는 서로 다른 선택자 약 77,000개에서 충돌 확률 50%에 이른다.

계약(`ELEMENT_SELECTOR_HASH_PATTERN = /^[0-9a-f]{1,16}$/i`)이 이미 16 hex 를 허용하므로 **계약 변경은 없다.** BigInt 없이 서로 다른 오프셋·소수를 쓰는 32비트 누산기 두 개를 각각 8 hex 로 0 패딩해 이어 붙인다(번들 부담 없음). 결과는 항상 정확히 16 hex 이므로 테스트로 폭을 고정할 수 있다.

## 2. 동일성 판정 (서버)

지문만으로는 구조와 속성이 완전히 같고 라벨만 다른 컨트롤을 가를 수 없다. 데모의 `리포트 내보내기` 와 `오류 발생` 이 그 경우다 — 둘 다 `main>div>button`, id·name·type 없음, 오직 적힌 글자만 다르다.

그 글자는 **이미 이벤트마다 저장된다**(`elementTextMaskedOrLimited`, 개인정보 규칙에 따라 마스킹·절단된 값). 새로 수집할 것이 없으므로 노출면이 늘지 않는다.

### 비교

탐지기가 요소 동일성을 `(elementSelectorHash, elementTextMaskedOrLimited)` **쌍**으로 판정한다. 두 필드가 모두 같을 때만 같은 요소다. 두 값 모두 없을 수 있으므로 `undefined === undefined` 는 같음으로 취급한다.

영향받는 곳은 두 종류다(`apps/api/src/detection/detect.ts`).

- **동등 비교** — `detectRageClicks:65` 의 연속 클릭 비교(현재 `event.elementSelectorHash === current.elementSelectorHash`). 여기가 허위 분노 클릭을 만드는 지점이다.
- **이슈 키 계산** — `selectorHash` 를 `makeIssue` 에 넘기는 모든 곳: `detectDeadClicks:45`, `detectRageClicks:79`, `detectLongPauses:101`, `detectErrorFriction:119`. 이 중 **실제로 동작이 바뀌는 것은 `detectDeadClicks` 뿐이다** — 이벤트마다 이슈를 만들지만 그 이슈의 키가 해시에서 나오므로, 서로 다른 버튼의 반응 없는 클릭이 지금은 한 이슈로 병합된다.
- `detectLongPauses` 와 `detectErrorFriction` 은 호출 형태만 기계적으로 바뀌고 동작은 그대로다. SDK 는 요소 메타데이터를 클릭에만 싣고(`collectors.ts:84` 의 click 리스너가 `getElementMetadata` 를 부르는 유일한 지점), idle 이벤트는 아예 발행하지 않는다. 따라서 두 함수가 넘기는 `event.elementSelectorHash` 는 항상 `undefined` 이고 키는 계속 `page` 다.
- `detectErrorFriction:119` 도 `selectorHash` 를 넘기지만 오류 이벤트에는 요소 메타데이터가 없어 값이 항상 `undefined` 다. 동작이 바뀌지 않는다.

### 이슈 id

**주의점:** `issueTargetKey`(`apps/api/src/detection/url.ts`)는 `[^a-z0-9|:_-]` 를 `_` 로 치환한다. 한글 글자를 id 에 그대로 넣으면 `저장` → `_`, `오류 발생` → `_` 가 되어 **둘이 다시 같아진다.**

따라서 글자를 id 에 직접 넣지 않는다. 서버에서 `(elementSelectorHash, elementTextMaskedOrLimited)` 를 hex 로 해시해 그 값을 이슈 키에 쓴다. 해시 입력은 두 값을 NUL 문자(`\u0000`)로 이어 붙인다. 마스킹된 글자에는 NUL 이 나타날 수 없으므로, 서로 다른 쌍이 경계가 겹쳐 같은 입력 문자열이 되는 일이 원천적으로 생기지 않는다.

`elementSelectorHash` 가 아예 없는 경우(오류 이벤트)는 지금처럼 리터럴 `"page"` 를 유지한다. 오류 이슈의 id 는 바뀌지 않는다.

이 서버측 해시 함수는 hex 만 출력하므로 id 안전 치환에 의해 뭉개지지 않는다.

## 3. 일회성 마이그레이션

배포 후 과거 이벤트는 옛 규칙 지문을 그대로 갖는다. `detectIssues` 는 배치마다 저장된 **전체** 이벤트에 대해 다시 돌고(`ingestion.ts:139`, `listEvents(projectId)`), 이벤트 보존은 기본값이 없어(`EVENT_RETENTION_DAYS` 미설정 시 무기한) 과거 이벤트가 만료되지 않는다. 방치하면 옛 규칙 이슈가 영구히 재생성되어 같은 버튼을 이중 집계한다.

`/trace.js` 는 `cache-control: no-store` 로 서빙되므로(`apps/api/src/routes/sdk-bundle.ts`) 브라우저가 SDK 를 캐시하지 않는다. 배포 직후 모든 클라이언트가 새 규칙을 쓰며, 옛 규칙 지문이 섞여 들어오는 기간이 없다.

### 절차

기존 마이그레이션은 컬럼 추가형이고 버전 카운터가 없다(`PRAGMA table_info` 확인 후 `ALTER TABLE`). 일회성 데이터 정리는 반복 실행되면 새 이벤트의 지문까지 지우므로 표시가 필요하다. 현재 쓰이지 않는 `PRAGMA user_version` 을 쓴다.

`SqliteStore.migrate()` 안에서 `user_version < 1` 일 때 한 번만:

```sql
UPDATE events SET element_selector_hash = NULL;
DELETE FROM issues
  WHERE substr(issue_id, -length('|page|' || issue_type)) <> '|page|' || issue_type;
PRAGMA user_version = 1;
```

세 문장은 `db.transaction` 으로 감싼다. `db.exec` 멀티스테이트먼트에는 암묵 트랜잭션이 없다.

- **지문 무효화** — 탐지기가 지문 없는 클릭을 이미 건너뛰므로(`detect.ts` 의 `filter(event => event.type === "click" && event.elementSelectorHash)`) 옛 규칙 이슈가 재생성되지 않는다.
- **해시로 키잉된 이슈 행만 삭제** — `issue_id` 형태는 `issue_{urlPath}|{키 ?? "page"}|{issueType}` 이다. `|page|` 를 부분문자열로 찾는 것은 **틀렸다**: `issueTargetKey` 의 허용 문자 클래스 `[a-z0-9|:_-]` 에 파이프가 들어 있고 `normalizePath` 도 파이프를 제거하지 않으므로(실측 `normalizePath("/settings|page") === "/settings|page"`), 경로에 파이프가 있으면 지문으로 키잉된 이슈가 `|page|` 를 포함해 삭제를 피한다. 또 `detectErrorFriction` 도 `elementKey(event)` 를 넘기므로(`detect.ts:116`) 지문을 실은 오류 이벤트는 `|page|` 없는 id 를 만들어 잘못 삭제된다. 따라서 **행 자신의 `issue_type` 으로 접미사를 정확히 비교한다** — 꼬리가 `|page|{타입}` 인 것은 키가 정확히 `page` 인 것과 동치이고, 키는 16 hex 아니면 `page` 이므로 이 판정은 증명적으로 정확하다(`/page/1` → `_page_1`, `/page` → `_page` 모두 `|page|` 를 포함하지 않는다). **오류 이슈는 살아남는다** — 트래픽이 멈춘 프로젝트도 오류 이슈를 잃지 않는다.

`MemoryStore` 는 영속 저장이 없어 마이그레이션 대상이 아니다.

### 대가

과거 클릭에서 나온 분노 클릭·반응 없는 클릭 이슈가 사라진다. 그 이슈들은 형제 요소를 뭉쳐 만든 틀린 이슈였다.

## 4. 남는 한계

이 설계로도 다음은 여전히 하나로 뭉친다. 알려진 한계로 기록하고 이번 범위에 넣지 않는다.

- **글자가 저장되지 않는 요소가 구조·속성까지 같은 경우.** 입력 계열과 민감 필드는 개인정보 규칙상 텍스트를 저장하지 않는다. 다만 그런 요소는 대개 `name`·`type` 을 갖고 있어 §1 의 속성 조각이 가른다.
- **`:` 없는 생성 id.** 무작위 UUID 를 id 로 쓰는 프레임워크는 렌더마다 다른 요소로 갈린다.
- **조상 3단 밖에서만 갈리는 요소.** 3단 위에서 처음 달라지는 두 컨트롤은 같은 지문을 갖는다.

반대 방향 — **하나여야 할 컨트롤이 여럿으로 갈리는** 한계도 남는다. §2 의 동일성 판정이 지문과 저장된 글자의 쌍을 보고, 그 글자는 `textContent` 가 비면 `aria-label` 로 폴백하기 때문이다(`sdk/src/dom.ts` 의 `allowedElementText`). 아래 두 항목은 **의도적으로 받아들인 대가**이며 버그가 아니다. 아이콘만 있는 버튼에서는 `aria-label` 이 유일한 라벨이라 그것을 신원에서 빼면 같은 행 안의 서로 다른 아이콘 버튼(`수정`·`삭제`)이 구분 불가로 합쳐진다 — 행 **안에서는** 필요하고 행 **사이에서는** 해롭다. 깔끔한 해법은 행 인식을 요구하고, 그것을 줄 수 있는 형제 순서번호(`nth-of-type`)는 §1 에서 의도적으로 금지했다. 정규식으로 라벨에서 이름만 벗겨내는 방안도 앞 단계에서 불가능으로 결론이 났다.

- **행마다 반복되는 텍스트 없는 컨트롤의 `aria-label` 이 레코드 주체를 담는 경우.** `<button aria-label="김철수 삭제"><svg/></button>` 같은 아이콘 전용 버튼은 지문이 같아도 라벨이 행마다 달라 **행당 하나의 요소**로 갈린다. `detectDeadClicks` 는 클릭마다 `elementKey(event)` 로 키를 매기므로 **행마다 이슈를 하나씩** 낸다. §5 의 "반복 컨트롤은 하나로 유지된다" 는 라벨까지 같은 경우로 한정된 기준이라 이 경우를 덮지 않는다. 완화가 하나 있다 — `redactText` 가 9자리 이상 숫자 덩어리를 `[redacted]` 로 접으므로 **숫자 행 id 는 정규화된다**(`주문 20250903001 취소` → `주문 [redacted] 취소` 로 모든 행이 같은 라벨). 사람 이름·상호처럼 글자로 된 주체는 접히지 않는다.
- **클릭할 때마다 라벨이 바뀌는 컨트롤.** `좋아요 12` → `좋아요 13` → `좋아요 14` 처럼 라벨이 카운터인 버튼은 연속 클릭이 매번 다른 요소가 되어, `detectRageClicks` 의 3초 창 판정(`detect.ts` 의 `sameElement(event, current)` + `cluster.length >= 3`)이 **3클릭을 절대 모으지 못한다**. 즉 카운터형 버튼에서는 **진짜 분노 클릭이 억제된다**. 놓친 이슈가 형제 버튼을 뭉쳐 만든 틀린 이슈보다 낫다는 판단으로 받아들인 결과다.

검토 결과 (2026-09-03): 위 두 항목을 사람이 검토하고 **현 상태 유지** 로 결정했다. 근거는 실제 제품 화면에 아이콘 전용 행 버튼이 있는지가 아직 확인되지 않았고, `aria-label` 을 신원에서 빼는 대안은 같은 행 안의 서로 다른 아이콘 버튼을 뭉치게 하는 반대 손실을 만들기 때문이다. 즉 이 두 항목은 미처리 과제가 아니라 **닫힌 결정**이다. 다시 열 조건은 하나다 — 실제 화면에 아이콘만 있는 행 버튼이 존재하고 그 버튼의 이슈가 행 수만큼 쏟아지는 것이 관측될 때.

## 5. 성공 기준

- 데모 페이지의 네 버튼(`저장`·`권한 추가`·`리포트 내보내기`·`오류 발생`)이 **네 개의 서로 다른 요소**로 인식된다. 실제 브라우저 클릭으로 확인한다 — 시드 데이터가 아니라 실수집으로 검증한다(이 결함을 시드 데이터가 숨겼기 때문이다).
- 구조·속성·라벨이 모두 같은 반복 컨트롤(목록 행의 `삭제`)은 **하나의 요소**로 유지된다.
- 지문이 항상 정확히 16 hex 이고 계약을 통과한다.
- `:` 를 포함한 id 를 가진 요소가 렌더 간 같은 지문을 갖는다.
- 마이그레이션이 두 번 실행돼도 새 이벤트의 지문을 지우지 않는다. 마이그레이션 후 옛 규칙 클릭 이슈 재생성 0건, 오류 이슈 유지.
- 두 스토어(SQLite·Memory)가 새 동일성 판정에서 같게 동작한다.
- SDK 번들이 gzip 10KB 예산 안에 있다(현재 4854B).
- 기준선 575 테스트가 계속 통과한다.
