# Trace 제품 재정의 — 사용자 행동 분석으로 간소화

작성일: 2026-09-30

## 왜 다시 정의하는가

2026-08-24 MVP 설계는 Trace를 "사용자가 막힌 지점을 자동으로 찾아주는 도구"로 정했다. 그 뒤 364커밋 동안 문제 감지, 와이어프레임 화면 미리보기, 팀·권한 관리, 세션 리플레이, 페이지 통계가 차례로 붙었다. 와이어프레임과 리플레이는 둘 다 "그때 사용자가 무엇을 보고 있었나"에 답하려는 기능이라 역할이 겹치고, 팀 관리는 MVP 설계에서 제외했던 범위였다.

이번에 만들려는 제품을 다시 정의했다. **막힌 곳 찾기가 아니라 사용자 행동 분석이다.** 이 문서는 새 정의와, 그 기준으로 남기고 걷어낼 것을 정한다. 이전 설계와 계획 문서는 모두 이 문서로 대체하고 삭제한다(git 이력에는 남는다).

## 제품 정의

> Trace는 사내 업무 시스템에 스크립트 한 줄로 붙이는 사용자 행동 분석 도구다. 사용자가 **어떤 기능을 많이 쓰는지**, **어떤 경로로 화면을 이동하는지** 보고, 궁금한 세션은 **리플레이로 직접 본다.**

- **POC 사용자:** 사내 제품팀의 PM과 기획자. 회사 업무 시스템에 붙여 여러 명이 함께 본다.
- **다음 단계:** 외부 회사가 설치해 쓰는 self-hosted 제품. 이 단계에서 필요한 것(감사 로그, 녹화 비율, 사용자 ID 연결 등)은 이번 범위에 넣지 않는다. 필요해지면 그때 설계한다.

## 확정한 결정

| # | 질문 | 결정 |
|---|---|---|
| 1 | 누가 쓰나 | POC는 사내 PM·기획자, 이후 외부 판매용 self-hosted |
| 2 | 핵심 가치 | 행동 분석: 기능 사용, 이동 경로, 세션 리플레이 |
| 3 | 기능 하나를 무엇으로 세나 | **화면 경로 + 클릭한 요소**. 스크립트가 자동으로 센다. 이름은 마스킹한 요소 글자 |
| 4 | 경로를 어떻게 보여주나 | **많이 다닌 경로 순위** 표. 경로 하나당 한 줄 |
| 5 | 어떤 세션을 녹화하나 | 리플레이가 켜진 프로젝트는 **모든 세션** |
| 6 | 로그인·팀 관리 | **허용 이메일 목록만.** 멤버와 역할 없음. 허용된 사람은 모든 프로젝트를 본다 |
| 7 | 세션과 방문자 | **탭 단위 세션**(sessionStorage, 30분 무활동 시 종료) + **익명 방문자 ID**(localStorage) |
| 8 | 관리자 화면 구성 | 메뉴 세 개: **기능 사용 · 이동 흐름 · 세션**. 첫 화면은 기능 사용 |
| — | `track()` | 걷어낸다. 받기만 하고 보여주는 곳이 없었고, metadata로 식별자가 새어 들어올 수 있다 |
| — | JS 오류 수집 | 걷어낸다 |

## 데이터 흐름

### 세션과 방문자
- **세션 ID:** 스크립트가 시작할 때 sessionStorage에서 `{ sessionId, lastActivityAt }`를 읽는다. 없거나 `lastActivityAt`이 30분보다 오래됐으면 새 세션 ID를 만든다. 이벤트를 보낼 때마다 `lastActivityAt`을 갱신한다. 새로고침하거나 페이지를 새로 불러오는 이동에도 같은 탭이면 세션이 이어진다. 새 탭은 새 세션이다.
- **방문자 ID:** localStorage의 `anon_` ID. 없으면 만든다.
- **동의 대기(`data-consent="pending"`):** 동의 전에는 두 저장소 모두에 쓰지 않고 메모리의 값만 쓴다. `grant()`가 오면 그때부터 저장한다. `deny()`가 오면 두 저장소에서 Trace 키를 지운다.
- **저장소를 쓸 수 없을 때**(접근이 예외를 던지거나 사생활 보호 모드): 예외를 삼키고 메모리 값으로 물러선다. 즉 페이지 단위 세션이 되지만 수집은 계속한다.
- **세션 길이:** 서버에서 그 세션의 첫 이벤트와 마지막 이벤트의 시간 차.

### 리플레이 녹화
- 프로젝트 설정에서 리플레이가 켜져 있으면, 동의가 있는 모든 세션을 처음부터 녹화한다.
- 조각은 일정 간격과 페이지 이탈 때 올린다. 간격과 크기 상한은 `shared/recording-limits.ts`의 기존 한도 안에서 계획 단계에서 정한다.
- 페이지를 새로 불러오면 rrweb이 새 전체 스냅샷부터 다시 기록한다. 조각 번호(`seq`)의 다음 값은 sessionStorage에 두어, 같은 세션의 조각으로 이어 붙인다.
- 재생기는 한 세션에 전체 스냅샷이 여러 번 있어도(페이지 전환) 끊기지 않고 이어서 재생한다.
- 마스킹 규칙과 기본 보존 기간 7일은 바꾸지 않는다.

### 집계 기준
모든 집계는 선택한 프로젝트와 기간(최근 1일·7일·30일, 기본 7일)으로 거른다. 미리 집계해 두는 테이블 없이 **조회할 때 SQLite에서 계산**한다. 지금의 페이지 통계처럼 이벤트 전부를 메모리로 읽지 않고, SQL 집계와 인덱스를 쓴다.

**화면 이름:** 경로(`urlPath`, 이미 `:id`로 정규화됨)마다 기간 안에서 가장 많이 나온 `titleMasked`를 쓴다. 제목이 없으면 경로를 그대로 쓴다.

**기능 사용**
- 기능 하나 = `(urlPath, elementKey)`. `elementKey`는 선택자 해시와 마스킹된 글자의 해시다.
- 기능 이름 = 마스킹된 요소 글자(`elementTextMaskedOrLimited`), 없으면 `elementRole`. 종류 표시 = `elementRole`.
- 기능 행: 클릭 수, 방문자 수(중복을 뺀 `anonymousUserId` 수).
- 화면 행: 방문 수(`page_view` 수), 방문자 수, 평균 체류, 이탈률. 체류와 이탈은 지금 `page-stats.ts`의 정의를 그대로 쓴다.
- 기본 정렬은 화면 방문 수. 화면 안의 기능은 클릭 수 순.

**경로 순위**
- 세션마다 `page_view`를 시간순으로 늘어놓고, 연달아 같은 경로가 나오면(새로고침) 하나로 합친다.
- 시작 화면을 "전체"로 두면 세션의 첫 화면부터, 특정 화면을 고르면 **그 세션에서 그 화면이 처음 나온 지점부터** 자른다. 그 화면이 없는 세션은 빠진다.
- 처음 5개 화면까지만 쓴다. 세션이 5개 화면 안에서 끝났으면 끝에 "이탈"을 붙인다.
- 같은 화면 순서끼리 묶어 세션 수를 세고, 많은 순으로 상위 20개를 보여준다. 비율 = 해당 경로 세션 수 ÷ 대상 세션 수.

**세션 목록 필터**
- 필터 없음: 기간 안 전체 세션, 최근 순.
- 기능 필터: 그 `(urlPath, elementKey)`를 한 번이라도 클릭한 세션.
- 경로 필터: 경로 순위와 같은 규칙으로 잘랐을 때 그 화면 순서와 일치하는 세션.
- 세션 행: 시작 시각, 방문자 ID 일부, 길이, 화면 수, 지나간 화면(최대 5개), 리플레이 유무.

### DB 스키마 변경
- 삭제: `issues`, `project_memberships`, `audit_logs`
- 유지: `projects`, `events`, `admin_users`, `admin_sessions`, `session_recordings`

## 관리자 화면

실제 관리자 화면의 토큰(`styles/tokens.css`)으로 그린 목업: [`2026-09-30-mockups/flow.html`](2026-09-30-mockups/flow.html)(이동 흐름, 위쪽 A안이 확정안이고 아래 B안은 채택하지 않음), [`2026-09-30-mockups/features-sessions.html`](2026-09-30-mockups/features-sessions.html)(기능 사용·세션·세션 창). 목업의 숫자는 예시다. 이 목업이 정하는 것은 **배치, 들어갈 내용, 화면 사이 이동**이다. 색과 간격은 기존 스타일을 따른다.

**공통:** 왼쪽 메뉴(위에 프로젝트 선택). 화면 오른쪽 위에 기간 선택(1일·7일·30일). 기간은 세 화면이 공유하고 URL에 남긴다.

**① 기능 사용 (첫 화면)**
- 지표 세 개: 방문자, 세션, 평균 세션 길이
- 화면·기능 이름 검색
- 표: 화면 행(펼치고 접기) 아래에 기능 행. 열은 방문·클릭 수, 방문자 수, 막대(방문자 기준), 평균 체류, 이탈률, [세션 보기]
- [세션 보기] → 세션 화면으로 가서 해당 화면 또는 기능 필터를 건다

**② 이동 흐름**
- 시작 화면 선택("전체" 또는 화면 하나)
- 표: 순위, 경로(화면 이름 칩을 `›`로 이음, 이탈은 점선 칩), 세션 수, 비율, 막대, [세션 보기]
- [세션 보기] → 세션 화면으로 가서 경로 필터를 건다

**③ 세션**
- 걸린 필터를 칩으로 보여주고 ✕로 푼다
- 표: 시작 시각, 방문자, 길이, 화면 수, 지나간 화면, 리플레이 유무, [열기]
- [열기] → 지금의 세션 창(화면 대부분을 덮는 다이얼로그). 왼쪽은 리플레이(재생, 배속, 화면 글자 보기), 오른쪽은 타임라인(화면 이동, 클릭, 스크롤 도달, 이탈)
- 새로 붙는 것: 타임라인 항목을 누르면 그 시점으로 재생 위치 이동, 재생 막대에 화면 전환 눈금
- 녹화가 없는 세션은 타임라인만 보여주고 "리플레이 없음"을 표시한다

**빈 상태:** 집계 결과가 없으면 설치 안내로 가는 링크를 보여준다.

## 진행 단계

작업 전에 `feature/demo-site`를 로컬 main에 fast-forward로 머지했다(2026-09-30). 작업 브랜치는 `.worktrees/` 아래에 로컬 HEAD 기준으로 만든다. 단계마다 구현 계획을 따로 쓰고, 단계가 끝날 때 테스트와 타입 검사가 모두 통과해야 한다.

## 실패 처리
- 저장소 접근 실패: 예외를 삼키고 메모리 값으로 물러선다. 수집은 멈추지 않는다.
- 녹화 조각 업로드 실패: 지금 업로더의 재시도와 영구 실패 처리를 그대로 쓴다.
- 녹화 없는 세션: 타임라인만 보여준다.
- 빈 집계: 빈 상태 화면을 보여준다.
- 집계 쿼리 실패: 지금 관리자 API의 오류 응답 형식과 화면의 오류 표시를 따른다.

## 테스트
- vitest를 그대로 쓴다. 저장소 테스트는 SQLite 메모리 DB 하나로 통일한다(`store-contract.test.ts`는 SQLite 대상으로 정리).
- 걷어내는 기능의 테스트는 코드와 함께 지운다. 남는 기능의 테스트는 계속 통과해야 한다.
- 새 테스트
  - SDK: 새로고침을 흉내 냈을 때 세션 유지, 30분 뒤 새 세션, 동의 대기 중 저장 금지, 거부 시 삭제, 저장소 예외 시 물러서기, 페이지를 넘는 조각 번호 이어 가기
  - 서버: 정해진 화면 순서의 샘플 데이터로 경로 순위(합치기, 자르기, 이탈 붙이기, 시작 화면 필터), 기능 집계, 세션 필터 세 종류
  - 관리자: 세 화면 컴포넌트, [세션 보기]가 올바른 필터로 이동하는지, 기간 공유
- 단계마다 끝날 때 데모 사이트(`npm run dev:demo`, 포트 3000)에서 직접 눌러 보고 스크린샷으로 확인한다. 로컬 DB를 새로 만들므로 데모용 프로젝트를 다시 만들고 허용 도메인을 `http://localhost:3000`으로 설정한다.
