# 행동 기록 — 무엇을 남기고 무엇으로 세는가

## 배경

2026-09-15 세션에서 리플레이 재생·미리보기 보완을 차례로 붙이다가 계속 같은 벽에 부딪쳤다. "이슈 없이 사용자 흐름을 보고 싶다", "사용자별로 보고 싶다" 는 요구가 매번 기존 구조와 어긋났다.

원인을 따라가 보니 새 요구가 아니었다. **구현이 원래 설계에서 빠뜨린 자리**였다.

### 원 설계가 말한 것

`2026-08-24-trace-mvp-design.md` 는 이 제품을 이렇게 정의했다.

> 최종 목표는 세션 리플레이까지 포함한 **행동 분석 제품**이지만, 첫 버전부터 전체 리플레이를 구현하지 않는다.
>
> 핵심 포지션: GA보다 쉬운 운영자용 행동 분석 도구. 숫자 대시보드보다 사용자가 막힌 지점을 **먼저** 알려준다.

즉 축은 **행동 분석**이고, 이슈는 그 진입점이다. 「문제 인박스」는 홈 화면이지 제품의 경계가 아니었다.

### 실제로 수집하는 것

계약(`eventTypeSchema`)에는 이벤트가 **16종** 정의돼 있다.

```
page_view  page_leave  click  scroll  idle  dead_click  rage_click
js_error  api_error  web_vital  custom_event  form_start
field_focus  field_blur  form_submit  form_abandon
```

SDK 가 실제로 보내는 것은 **3종**이다 — `page_view` · `click` · `js_error` (`collectors.ts`).

### SPA 라우팅을 감지하지 않는다

`page_view` 는 `installCollectors` 가 도는 **최초 1회**만 보낸다(`collectors.ts:72`). `pushState`·`popstate`·`hashchange` 를 듣지 않는다.

사용자 앱(SPA, 해시 라우팅)에서 실제로 잰 값이다.

| 항목 | 값 |
| --- | --- |
| 이벤트 | 20건 |
| 세션 | 5개 |
| **경로** | **2개** (`/`, `/popup`) |
| 이벤트 종류 | 2가지 (`page_view`, `click`) |

경로 2개 중 `/popup` 은 별도 창이 따로 로드된 것이다. **SPA 안에서 화면을 아무리 옮겨 다녀도 기록은 `/` 한 줄이다.** "어떤 페이지를 거쳤나" 에 답할 데이터가 없다.

다행히 경로 정제는 이미 준비돼 있다 — `parseHashRoute`(`privacy.ts:99`)가 `#/foo`·`#!/foo` 를 경로로 풀어낸다. 보내기만 하면 된다.

### 세션과 사용자

원 설계의 `Session` 은 엔티티였다 — `session_id`·`anonymous_user_id`·`started_at`·`ended_at`·`device`·`browser`·`os`·`viewport`·`referrer`.

구현에는 **세션 테이블이 없다.** 세션은 이벤트의 `session_id` 문자열로만 존재한다. `anonymous_user_id` 는 배치 봉투로 올라와 정제까지 되지만 `events` 에 컬럼이 없어 버려진다.

`TraceClient` 는 세 ID 를 클래스 필드로 만든다(`client.ts:58-60`). 쿠키·localStorage·sessionStorage 를 쓰지 않으므로 **새로고침하면 셋 다 새 값**이다. 같은 사람의 두 방문을 이을 수단이 없다.

## 목표

- **한 방문 안의 흐름이 온전히 남는다.** 어떤 페이지를 거쳐 무엇을 누르고 얼마나 내렸는지.
- 그 기록으로 **페이지 기준 통계**를 센다 — 방문·체류·이탈·스크롤 도달.
- 이슈는 통계의 하나가 된다. 「문제 인박스」를 지우지는 않는다.
- **설치는 지금 그대로 스크립트 한 줄.**

## 목표가 아닌 것

- **사용자 식별.** 쿠키·스토리지·`identify()` 를 쓰지 않는다. 한 방문 = 한 세션으로 둔다. 필요해지면 나중에 얹어도 이 설계가 깨지지 않는다(§6).
- **`Session` 엔티티 신설.** 이벤트 집계로 충분한지 먼저 확인한다.
- **대시보드 재편.** 통계 화면을 새로 놓되 홈 구성은 데이터가 쌓인 뒤에 다시 본다.
- **나머지 11종 이벤트.** `form_*`·`web_vital`·`api_error`·`idle` 은 이번에 안 만든다.

## 1. 라우팅마다 `page_view`

`history.pushState`·`replaceState` 를 감싸고 `popstate`·`hashchange` 를 듣는다. 경로가 **실제로 바뀐 경우에만** 보낸다 — SPA 는 같은 경로로 `replaceState` 를 자주 부르고, 거르지 않으면 같은 화면이 수십 줄 쌓인다.

비교 기준은 정제된 경로(`redactUrl(location.href).urlPath`)다. 쿼리만 바뀐 이동은 같은 페이지로 본다.

**Navigation API 를 쓰지 않는다.** Chrome 계열 전용이라 self-hosted 고객의 브라우저를 가른다. `history` 패치는 오래된 방식이지만 어디서나 돈다.

## 2. `page_leave` 와 체류 시간

`pagehide` 에서 직전 페이지의 `page_leave` 를 보낸다. 라우팅으로 페이지를 떠날 때도 같은 이벤트를 먼저 보낸다.

체류 시간은 **저장하지 않는다.** `page_view` 와 다음 `page_leave` 의 시각 차이로 조회 시점에 계산한다 — 중복 저장하면 둘이 어긋날 때 무엇이 맞는지 알 수 없다.

**`visibilitychange` 는 쓰지 않는다.** 탭 전환마다 이탈로 잡히면 체류가 잘게 쪼개지고, 돌아왔을 때 이어 붙일 방법이 없다. 탭을 오래 띄워 둔 채 떠난 세션의 체류가 과다 계상되는 것은 이 선택의 대가다.

## 3. `scroll` 은 마일스톤만

깊이 **25 · 50 · 75 · 100%** 도달 시점만 보낸다. 페이지당 최대 4건이라 이벤트 수가 상수로 묶인다.

깊이는 **화면 바닥 기준**으로 잰다.

```
depth = (scrollTop + viewportHeight) / documentHeight
```

문서 맨 위에서 이미 화면 한 칸을 보고 있으므로, 짧은 문서일수록 시작 깊이가 높다. `scrollTop / (documentHeight - viewportHeight)` 로 재면 "얼마나 움직였나" 가 되어 문서 길이에 따라 같은 25% 가 다른 의미가 된다.

- 되돌아 올라가도 다시 보내지 않는다(이미 지난 마일스톤).
- 라우팅으로 페이지가 바뀌면 마일스톤을 초기화한다.
- 문서가 뷰포트보다 짧아 스크롤이 불가능한 페이지는 아무것도 보내지 않는다 — 100% 를 즉시 보내면 "끝까지 읽었다" 와 구분되지 않는다.

## 4. 흐름을 보는 화면

이미 만들어 둔 것이 있다(커밋 전, 워크트리).

- **세션 목록** — `events` 를 `session_id` 로 묶어 최근 순. 기록 유무를 한 컬럼으로 표시하고, 있는 행에만 재생 버튼을 붙인다.
- **세션 상세 다이얼로그** — 세션 타임라인을 80% x 90% 다이얼로그로 연다.

새 이벤트가 들어오면 타임라인이 이렇게 읽힌다.

```
10:04:04  page_view   /설정
10:04:06  click       저장
10:04:09  scroll      75%
10:04:12  page_view   /목록
10:04:30  page_leave  /목록
```

## 5. 페이지 기준 통계

새 화면 하나에 페이지별로 센다.

| 지표 | 계산 |
| --- | --- |
| 방문 수 | `page_view` 개수 |
| 평균 체류 | `page_view` → 그 세션의 다음 `page_leave` 차이의 평균. **짝이 없는 방문은 평균에서 뺀다** — 0 으로 세면 브라우저가 강제 종료된 세션이 평균을 끌어내린다 |
| 이탈률 | 그 페이지가 세션의 마지막 `page_view` 인 비율 |
| 스크롤 도달 | 25·50·75·100 각각 도달한 방문의 비율 |

기존 「문제 인박스」는 그대로 둔다. 통계가 주역이 되면 홈 구성은 그때 다시 본다.

## 6. 사용자 식별을 나중에 얹을 수 있는가

얹을 수 있다. 이 설계는 세션을 이벤트의 묶음으로만 다루므로, 나중에 `anonymous_user_id` 를 `events` 에 저장하거나 `Session` 엔티티를 넣어도 위 화면과 통계는 그대로 돈다 — 묶는 열이 하나 늘 뿐이다.

다만 그때 결정해야 할 것이 둘 있다.

- **브라우저에 식별자를 저장할 것인가.** README 첫 줄의 "쿠키·localStorage·sessionStorage 를 사용하지 않습니다" 가 바뀐다. 동의 배너가 필요한 지역에서는 법적 판단이 따라온다.
- **`identify()` 로 내부 ID 를 받을 것인가.** 원 설계에 있던 방식이다. 사이트가 로그인 상태를 알고 있으면 가능하지만, 익명 수집이라는 성격이 바뀐다.

## 7. 검증

### 단위

- 같은 경로로 `replaceState` 를 반복해도 `page_view` 가 한 번만 나간다
- 해시 라우트(`#/settings`)가 `/settings` 로 기록된다
- 라우팅으로 페이지를 떠나면 직전 경로의 `page_leave` 가 먼저 나간다
- 스크롤 마일스톤이 각 구간당 한 번만, 되돌아 올라가도 다시 안 나간다
- 스크롤 불가능한 문서는 아무것도 안 보낸다
- 라우팅 후 마일스톤이 초기화된다

### 실측

사용자 앱(SPA, 해시 라우팅)에서 화면을 옮겨 다니며 잰다.

- **경로가 2개에서 몇 개로 늘어나는가** — 이 스펙이 고치려는 것이 이 숫자다
- 한 세션의 타임라인이 흐름으로 읽히는가
- 이벤트 수가 감당할 만한가 (세션당, 배치당)

## 8. 남는 한계

- **세션이 페이지 로드 하나다.** 새로고침하면 끊긴다. SPA 라 자주 일어나지는 않지만, 끊긴 두 조각을 잇는 방법은 없다.
- **탭을 띄워 둔 채 떠난 세션의 체류가 과다 계상된다.** `visibilitychange` 를 안 쓰기로 한 대가다.
- **체류 시간은 마지막 페이지에서 계산되지 않는다.** `pagehide` 가 못 나가면(브라우저 강제 종료 등) 그 페이지는 체류를 모른다.
- **슬래시 없는 해시 라우팅(`#dashboard`)은 감지하지 못한다.** `redactUrl` 은 `#/reports`·`#!/report` 는 경로로 풀어내지만 `#dashboard` 는 `/` 로 남는다 — 페이지 내 앵커 이동과 구분할 방법이 없어서다. 앵커로도 취급하면 이 라우팅을 안 쓰는 일반 사이트에서 앵커를 누를 때마다 `page_view` 가 잘못 생긴다. 더 넓은 실패라 이 선택을 그대로 둔다. 이런 방식으로 라우팅하는 SPA 는 이 브랜치 이전과 같은 동작을 하고, 페이지 통계는 방문 전체가 `/` 한 줄로 보인다 — 이탈률 1.0, 체류가 방문 전체로 늘어나고, 스크롤 도달은 화면 전체에서 가장 깊이 내려간 지점으로 뭉친다. 완전해 보이지만 틀린 값이다.
- **스크롤 마일스톤은 네 칸이다.** 30% 에서 멈춘 사용자와 50% 에서 멈춘 사용자가 같은 값(25%)으로 보인다.
- **화면 셸이 고정되고 안쪽 패널만 스크롤하는 앱은 스크롤 깊이를 낼 수 없다.** `installScrollWatcher` 는 `documentHeight <= viewportHeight` 면 아무것도 보내지 않는다 — 스크롤이 불가능한 문서로 보고 100% 를 즉시 보내는 것을 피하려는 의도된 동작이다(§3). 그런데 뷰포트 자체가 아니라 안쪽 컨테이너가 스크롤되는 앱은 정확히 이 조건이다 — 실측한 사용자 앱(Amaranth 10)이 `document.documentElement.scrollHeight === window.innerHeight`(772 = 772) 였고, 실제로 이 방문에서 스크롤 이벤트는 0 건이었다. 셸 고정형 앱에서는 스크롤 도달 통계가 항상 0 으로 남는다.
- **뷰포트보다 살짝만 긴 페이지는 한 픽셀만 내려도 여러 구간에 동시에 도달한 것으로 찍힌다.** 깊이를 화면 바닥 기준으로 재는 설계(§3) 때문이다 — 문서가 뷰포트의 1.3 배 길이면 스크롤 시작점이 이미 depth 77% 이므로, 스크롤 한 번에 25·50·75% 가 한꺼번에 찍힌다. 페이지 통계의 25%·50% 도달률은 "그 지점까지 읽었다" 가 아니라 "그 페이지 길이에서 조금이라도 내렸다" 로 읽어야 하는 값이다 — 운영자가 오독하기 쉬운 숫자다.
- **미리보기로는 "어떤 버튼" 을 확인하기 어렵다.** 클릭 위치를 상자로 보여줄 뿐이고 요소 글자는 스위치를 켜야 보인다. 타임라인이 그 답을 더 정확히 준다 — 미리보기의 자리는 이 스펙이 정하지 않는다.
- **이벤트 양이 늘어난다.** 이전에는 SDK 가 `page_view`·`click`·`js_error` 3 종만 보냈다. 이 브랜치 이후 화면 7개짜리 세션 하나가 이벤트 20건을 낸다(`page_view` 7·`page_leave` 7·`click` 6, 실측) — 세션당으로도, 배치 수로도 늘어난다(스크롤 폭주가 배치 전송 20건 문턱을 더 자주 건드린다). `detectIssues` 는 배치마다 프로젝트의 **전체** 이벤트를 다시 훑으므로(`ingestion.ts:137`, 이미 `2026-09-03-element-identity-design.md` 에 적힌 성질이다) 이벤트가 늘어난 만큼 그 계산량도 늘어난다. `EVENT_RETENTION_DAYS` 는 기본값이 없어 설정하지 않으면 이벤트가 무기한 쌓인다 — 운영자에게 이 설정을 켜도록 권한다.
- **배포하면 기존 프로젝트의 이슈 수가 눈에 띄게 바뀐다.** `detectDeadClicks`(`detect.ts:32`) 는 클릭 뒤에 `page_view` 가 오면 "화면이 반응했다" 로 본다. 이 브랜치 이전에는 SPA 에서 라우팅을 일으키는 클릭이 `page_view` 없이 끝나 dead click 으로 잘못 잡혔다. 이제 그 `page_view` 가 실제로 나가므로 이 오탐이 사라진다 — 이슈 수와 문제 인박스가 배포 직후 줄어드는 것처럼 보일 수 있다. 회귀가 아니라 이 브랜치가 고친 오탐이 없어진 것이다.
