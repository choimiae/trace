# 대표 이벤트 선택 — 이슈가 자기 요소의 클릭을 근거로 쓴다

## 배경

관리자에서 이슈를 열면 위쪽에 화면 미리보기가 뜬다. 그 그림은 새로 그리는 것이 아니라 수집된 이벤트 하나를 골라 그 이벤트가 실은 `screenContext` 를 그린 것이다. 고르는 곳은 `findRepresentativeEvent`(`apps/api/src/routes/admin-proxy.ts:527`)다.

후보를 좁히는 조건이 `projectId` · `sessionIds`(최대 3) · `urlPath` · 시간창 · 이벤트 타입 다섯 개뿐이고 **요소 신원이 없다.** 그래서 한 세션에서 나온 이슈들이 같은 클릭을 근거로 쓴다. 2026-09-02 실측에서 `권한 추가` 8회 반복 클릭 이슈의 근거 표가 58ms 앞선 `저장` 클릭을 표시했다.

시간창은 `firstSeenAt − REPRESENTATIVE_LEAD_IN_MS(30초)` 부터라 이슈 자신보다 앞선 이벤트도 후보에 든다. 이것이 위 사례의 직접 원인이다.

사용자에게 보이는 피해는 이미 한 겹 눌러 두었다 — 화면 맥락 2단계에서 근거 표의 라벨을 `클릭` → `화면 내 클릭` 으로 낮춰 **거짓 진술은 막혀 있다.** 남은 것은 근거의 질 저하다. 운영자가 `권한 추가` 문제를 보면서 `저장` 버튼이 눌린 화면을 본다.

### 이번에 측정해서 알게 된 것 (2026-09-04)

설계의 갈래가 여기서 갈리므로 추측 대신 실수집으로 확인했다.

**클릭은 예외 없이 화면 맥락을 싣는다.** 데모에서 버튼 4종 · 입력 3종 · 링크 4종 · 제목/라벨/설명 텍스트 · 빈 여백을 눌러 클릭 19건을 수집했고, **19건 모두** `screenContext` 와 클릭 지점(`target`)을 가졌다. 코드도 같은 말을 한다 — `collectors.ts:85` 가 모든 클릭에서 `getScreenContext` 를 부르고, 그 함수(`sdk/src/dom.ts:359`)는 DOM 예외가 날 때만 `undefined` 를 돌려준다. 서버 검증(`sanitizeScreenContext`)에서 떨어지는 경우도 측정에서는 0건이었다.

**클릭이 아닌 이벤트는 화면 맥락을 전혀 싣지 않는다.** SDK 는 클릭 리스너에서만 만들기 때문이다. `page_view` · `js_error` · `custom_event` 가 모두 그렇다.

**SDK 가 실제로 발행하는 타입은 `page_view` · `click` · `js_error` 셋뿐이다**(`custom_event` 는 앱이 `window.trace.track` 을 부를 때). 계약(`packages/shared/src/events.ts:10` 의 `eventTypeSchema`)에는 16종이 있지만 `dead_click` · `rage_click` · `idle` · `scroll` · `form_*` 은 아무도 발행하지 않는다. 따라서 `REPRESENTATIVE_EVENT_TYPES` 의 유형별 선호 목록은 실질적으로 전부 `click` 으로 귀결된다. `error_friction` 의 1순위가 `js_error` 인데 오류 이벤트에는 화면 맥락이 없어 화면 맥락을 요구하는 조회에 절대 걸리지 않는다 — 이것이 "구조적으로 항상 틀린다" 의 정체다.

## 목표

- 요소를 아는 이슈는 **그 요소의 클릭만** 근거로 쓴다. 형제 버튼의 화면을 빌려오지 않는다.
- 요소를 아는 이슈의 대표 이벤트는 **이슈 자신의 시간 구간 안**에 있다.
- 요소를 모르는 이슈(`long_pause` · `error_friction`)의 동작은 변하지 않는다.
- 기존 이슈 행이 마이그레이션으로 사라지지 않는다.

## 목표가 아닌 것

- **이슈 id 파싱.** 요소 키는 이슈 id 안에 이미 들어 있지만, id 를 파싱하는 코드는 저장소 전체에 0건이고 그 성질은 유지할 가치가 있다. 필드로 따로 싣는다.
- **폴백.** 이슈의 요소에 화면 맥락을 가진 클릭이 없으면 대표 이벤트를 비운다. 같은 화면의 다른 클릭으로 대신 채우지 않는다. 위 측정에 따르면 요소를 아는 이슈에서 이 경우는 사실상 생기지 않는다 — 근거가 되는 클릭이 곧 화면 맥락을 가진 클릭이기 때문이다. 그럼에도 규칙으로 못박는 이유는, 틀린 근거를 보여주느니 비우는 편이 낫다는 판단이다.
- **`error_friction` 이 자기 화면을 갖게 만들기.** 근본 해결은 SDK 가 오류 시점에 화면 맥락을 싣는 것이다. SDK 수집 · 계약 · 번들 예산 · 개인정보 검토가 모두 걸리므로 별도 작업. 이번에는 오류 이슈가 주변 클릭을 빌려오는 현재 동작을 그대로 둔다. 근거 표 라벨이 이미 `화면 내 클릭` 이라 거짓 진술은 아니다.
- **`REPRESENTATIVE_EVENT_TYPES` 정리.** 발행되지 않는 타입이 목록에 남아 있는 것은 SDK 가 나중에 그 타입을 낼 여지를 둔 것이다. 요소 키가 있는 경로에서만 이 목록을 건너뛰고, 목록 자체는 손대지 않는다.
- **`upsertIssues` 의 생존 이슈 정리.** 삭제 경로가 없어 낡은 이슈 행이 영구히 남는 문제는 별개 작업이다.
- **이벤트 보존 정책.** `EVENT_RETENTION_DAYS` 미설정 시 무기한인 것은 그대로 둔다.

## 1. 두 부류로 갈라 다루기

측정 결과가 이슈를 두 부류로 깨끗하게 가른다. 이 구분이 설계의 뼈대다.

**A. 근거가 클릭 자체인 이슈** — `rage_click`, `dead_click_cluster`

이슈를 만든 이벤트가 클릭이고, 그 클릭은 화면 맥락을 갖고 있다. 이슈에 어느 요소인지만 실으면 그 요소의 클릭만 골라낼 수 있다.

**B. 근거 이벤트에 화면 맥락이 없는 이슈** — `long_pause`, `error_friction`

멈춤 · 오류에는 화면 맥락이 없다. 주변 클릭을 빌려올 수밖에 없고, 어느 요소인지도 알 수 없다.

규칙은 한 줄이다.

> 요소를 아는 이슈는 그 요소의 클릭만 쓰고, 창을 이슈 자신의 시간 구간으로 좁힌다.
> 요소를 모르는 이슈는 지금 그대로 — 주변 클릭을 빌려오고 30초 앞까지 본다.

### lead-in 을 A 에서만 빼는 근거

`REPRESENTATIVE_LEAD_IN_MS` 는 B 부류를 위해 존재한다. 멈춤 · 오류 이슈는 `firstSeenAt` 과 `lastSeenAt` 이 같은 한 시점이고 화면 맥락은 그 직전 클릭에 실리므로, 창을 그 시점으로만 잡으면 대표 화면이 사라진다. **B 에서는 유지한다.**

A 에서는 뺀다. 그 이슈를 만든 클릭들은 정의상 이슈 시간 구간 안에 있고, 측정에 따르면 전부 화면 맥락을 갖는다. 창을 넓힐 이유가 없고, 넓히면 이슈 시간대 밖 프레임이 뜰 여지만 생긴다. 빼면 "보이는 이벤트는 항상 이슈 시간창 안" 이라는 성질을 얻고 테스트로 못박을 수 있다.

## 2. 요소 키를 실어 나르기

요소 키는 `elementKey`(`apps/api/src/detection/element-identity.ts:16`)가 만드는 `hash64Hex(지문 + NUL + 마스킹된 글자)` 다. 항상 정확히 16 hex 이거나, 지문이 없으면 `undefined` 다.

### 계약

`issueSchema`(`packages/shared/src/events.ts`)에 `elementKey` 를 선택 필드로 더한다. 폭은 **정확히 16 hex** 로 못박는다 — `hash64Hex` 출력이 항상 그 폭이므로 계약을 좁혀도 정상 값이 거절되지 않는다.

기존 `ELEMENT_SELECTOR_HASH_PATTERN`(`privacy.ts:13`)은 `/^[0-9a-f]{1,16}$/i` 로 1~16 을 허용한다. 그것을 재사용하지 않는 이유는, 그 폭이 32비트 시절의 8 hex 지문을 받아 주려고 열어 둔 것이고 요소 키에는 해당하지 않기 때문이다. 짧은 값이 들어오면 그것은 정상 값이 아니라 결함이므로 계약이 잡아야 한다.

새 노출이 아니다. 이 값은 이미 마스킹된 두 값의 단방향 해시이고, 그 원본인 `elementSelectorHash` 는 이벤트에 실려 이미 관리자에게 간다.

### 탐지기

`makeIssue`(`apps/api/src/detection/detect.ts:138`)는 이미 `elementKey` 를 입력으로 받아 이슈 id 를 만드는 데 쓴다. 같은 값을 반환 객체에도 싣는다. 호출부 네 곳(`detectDeadClicks` · `detectRageClicks` · `detectLongPauses` · `detectErrorFriction`)은 변경이 없다 — 뒤의 둘은 지금도 `undefined` 를 넘긴다.

### 저장

**이벤트 테이블에도 같은 키를 저장한다.** 조회 시점에 SQL 로 정확히 거르기 위해서다. SQLite 에는 `hash64Hex` 가 없으므로 `WHERE` 절에서 키를 만들어 낼 수 없고, 읽은 뒤 JS 에서 거르면 세션당 후보 상한(`SCREEN_CONTEXT_CANDIDATE_LIMIT`, `store/types.ts:97` 의 10) 안에 그 요소의 클릭이 없을 때 조용히 실패한다. 이 결함이 오래 안 걸린 이유가 "웬만하면 맞았기 때문" 이므로 같은 함정을 다시 파지 않는다.

- `events.element_key TEXT` — `saveBatch`(`sqlite-store.ts:462`)가 `elementKey(event)` 를 불러 넣는다.
- `issues.element_key TEXT` — `upsertIssues`(`sqlite-store.ts:517`)가 넣는다.

대안 둘을 검토하고 버렸다. **이슈에 (지문, 마스킹된 글자) 쌍을 싣는 안**은 파생값을 저장하지 않아 정의 변경에 강하지만, 마스킹됐어도 사용자 화면의 글자가 이슈 행과 관리자 API 응답에 복제된다. **후보를 넉넉히 읽어 JS 에서 거르는 안**은 스키마 변경이 가장 작지만 위의 조용한 실패가 남는다.

받아들이는 대가: 파생값을 저장하므로 `elementKey()` 정의가 바뀌면 저장값이 낡는다. 생산자가 그 함수 하나뿐이라 관리되고, 정의를 바꾸는 일은 어차피 데이터 마이그레이션을 동반한다(요소 신원 작업이 실제로 그랬다).

### 조회

`ScreenContextEventQuery`(`store/types.ts:108`)에 `elementKey?: string` 를 더하고 두 스토어가 함께 구현한다.

- SQLite(`sqlite-store.ts:575`): `AND element_key = ?` 를 조건에 더한다. 상한이 이미 걸러진 행에만 적용되므로 위의 조용한 실패가 생기지 않는다.
- Memory(`memory-store.ts:324`): 같은 비교를 필터에 더한다. 메모리 스토어는 이벤트 객체를 그대로 들고 있으므로 `elementKey(event)` 를 그 자리에서 부른다.

`elementKey` 를 넘기지 않으면 조건이 붙지 않아 지금 동작 그대로다.

### 조회부

`findRepresentativeEvent` 가 이슈의 `elementKey` 유무로 갈린다.

- **있으면** — `elementKey` 를 넘기고, 창을 `[firstSeenAt, lastSeenAt]` 로 잡고, 조회를 **한 번만** 한다. 화면 맥락을 가진 이벤트가 클릭뿐이므로 `REPRESENTATIVE_EVENT_TYPES` 로 선호 타입을 거는 단계가 의미를 잃는다. 코드 경로가 하나 줄어든다.
- **없으면** — 지금 그대로. 30초 lead-in, 선호 타입 조회 후 폴백 조회.

## 3. 마이그레이션

두 컬럼 모두 기존 패턴을 따른다 — `hasColumn` 확인 후 `ALTER TABLE`. `PRAGMA user_version` 은 쓰지 않는다. 요소 신원 작업의 일회성 데이터 정리와 달리 이번은 컬럼 추가뿐이라 반복 실행돼도 무해하다.

```sql
ALTER TABLE events ADD COLUMN element_key TEXT;
ALTER TABLE issues ADD COLUMN element_key TEXT;
```

**백필이 없다.** 요소 신원 마이그레이션(`user_version = 1`)이 기존 이벤트의 `element_selector_hash` 를 이미 `NULL` 로 만들었으므로, 옛 이벤트의 요소 키는 어차피 `undefined` 다. 새 컬럼이 `NULL` 인 것이 정확히 맞는 값이다.

**기존 이슈 행**은 `element_key` 가 `NULL` 이다. `NULL` 이면 요소 필터를 걸지 않으므로 지금 동작으로 떨어진다. 탐지기는 배치마다 저장된 전체 이벤트에 대해 다시 돌고(`ingestion.ts:139`) `upsertIssues` 로 덮어쓰므로, **트래픽이 있는 프로젝트는 다음 배치에서 저절로 채워진다.** 별도 정리 작업이 없다.

`INSERT OR REPLACE INTO issues` 와 `INSERT OR IGNORE INTO events` 는 컬럼 목록 · 플레이스홀더 · `run()` 인자를 각각 하나씩 늘려야 한다. 셋이 어긋나면 타입 오류가 아니라 실행 시점 오류이므로 왕복 테스트로 잡는다.

`MemoryStore` 는 영속 저장이 없어 마이그레이션 대상이 아니다.

## 4. 검증

이 결함이 오래 안 걸린 이유가 검증을 전부 손으로 해시를 다르게 넣은 시드 데이터로 했기 때문이므로, 검증을 두 겹으로 둔다.

### 자동 테스트

**계약** — `issueSchema` 가 `elementKey` 를 16 hex 로만 받는다.

**탐지기** — `rage_click` · `dead_click_cluster` 이슈는 키를 싣고 `long_pause` · `error_friction` 은 싣지 않는다. 그리고 **이슈 id 안에 들어간 키와 필드 값이 같다** — 두 경로가 따로 놀지 않게 못박는다.

**스토어 계약** (`store-contract.test.ts` 는 이미 두 스토어를 같은 검사로 돌린다)

- 같은 화면 · 같은 세션 · 같은 시간창에 요소 A · B 의 클릭이 있을 때 `elementKey: A` 로 조회하면 A 만 나온다
- 지문은 같고 마스킹된 글자만 다른 형제 버튼이 갈린다 — 이번 결함의 핵심 사례
- `elementKey` 를 넘기지 않으면 지금처럼 둘 다 후보다
- `element_key` 가 `NULL` 인 옛 이벤트는 키를 넘긴 조회에 걸리지 않는다
- `elementKey` 를 실은 이슈가 저장 후 그대로 돌아온다 (arity 왕복)

**조회부** (`admin.test.ts`)

- 요소 키가 있는 이슈: 시간창 안에 다른 요소의 클릭이 있어도 대표로 뽑히지 않는다
- 요소 키가 있는 이슈: 이슈 구간 밖(lead-in 자리)의 **같은 요소** 클릭도 뽑히지 않는다 — lead-in 제거를 못박는다
- 요소 키가 없는 이슈(`error_friction`): 지금처럼 30초 앞 클릭이 뽑힌다 — 기존 동작 유지를 못박는다
- 일치가 없으면 `representativeEvent` 가 없다

**마이그레이션** — 컬럼 없는 기존 DB 를 열면 컬럼이 생기고, 두 번 열어도 안전하고, 기존 이슈 행이 사라지지 않는다.

### 실수집 검증 (시드 금지)

데모 사이트에서 `저장` · `권한 추가` · `리포트 내보내기` · `오류 발생` 을 섞어 누르고 관리자에서 확인한다.

- 각 이슈의 근거 표에 뜨는 `화면 내 클릭` 이 그 이슈의 버튼과 일치한다
- 지문이 같은 `리포트 내보내기` / `오류 발생` 쌍이 서로의 화면을 빌려오지 않는다
- 2026-09-02 에 관측된 회귀가 재현되지 않는다 — `권한 추가` 반복 클릭 이슈가 `저장` 클릭을 표시하지 않는다

## 5. 성공 기준

- 실수집에서 요소 키가 있는 모든 이슈의 대표 이벤트가 **그 이슈의 요소 클릭**이다
- 요소 키가 있는 이슈의 대표 이벤트 시각이 항상 이슈 시간 구간 안이다
- `error_friction` · `long_pause` 의 대표 이벤트 선택 동작이 변하지 않는다
- 마이그레이션 후 기존 이슈가 사라지지 않고, 다음 수집 배치에서 `element_key` 가 채워진다
- 두 스토어(SQLite · Memory)가 새 조회 조건에서 같게 동작한다
- 기준선 623 테스트가 계속 통과한다

## 6. 남는 한계

- **`error_friction` 은 여전히 남의 화면을 빌려온다.** 오류 이벤트에 화면 맥락이 없다는 구조가 그대로이기 때문이다. 근거 표 라벨이 `화면 내 클릭` 이라 거짓 진술은 아니지만, 그 클릭이 오류와 무관한 요소일 수 있다. 닫으려면 SDK 가 오류 시점에 화면 맥락을 실어야 한다.
- **`long_pause` 도 마찬가지다.** 다만 멈춤은 성격상 "직전에 뭘 하고 있었나" 가 근거로 타당해 피해가 작다.
- **저장된 요소 키는 파생값이다.** `elementKey()` 정의가 바뀌면 이벤트 테이블의 값이 낡는다. 그때는 JS 로 전체 이벤트를 다시 훑는 마이그레이션이 필요하다.
- **키가 아직 안 채워진 이슈는 옛 동작을 한다.** 트래픽이 멈춘 프로젝트의 기존 이슈는 `element_key` 가 `NULL` 로 남아 형제 요소의 화면을 계속 보여줄 수 있다. 그 프로젝트의 이슈 목록 자체가 이미 갱신되지 않는 상태이므로 받아들인다.
