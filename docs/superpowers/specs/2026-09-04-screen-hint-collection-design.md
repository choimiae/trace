# 화면 힌트 수집 — 이름이 아니라 그려진 것으로 고른다

## 배경

관리자에서 이슈를 열면 `ScreenContextPreview` 가 화면 미리보기를 그린다. 그 그림은 이벤트에 실린 `screenContext.layoutHints` 를 사각형으로 옮긴 것이고, 힌트를 만드는 곳은 `collectLayoutHints`(`packages/sdk/src/dom.ts:280`)다.

실제 제품(Amaranth 10)에서 미리보기가 거의 그려지지 않는다는 보고를 받고 2026-09-04 에 조사했다.

### 측정한 것

**ONEFFICE 문서 팝업 화면** (`localhost:3000/#/popup`, 뷰포트 1456×828):

| 항목 | 값 |
|---|---|
| 보이는 요소 | 633 |
| 랜드마크(`header`·`nav`·`main`·`aside`·`role=…`) | **0** |
| 이웃 후보(`button`·`a[href]`·`input`·`select`·`textarea`·`h1~h3`) | **3** |
| 실제 저장된 힌트 | **3** |

저장된 힌트 수가 후보 수와 정확히 같다. **수집기는 잡을 수 있는 것을 다 잡았고, 후보가 3개뿐이었다.** 상한(`MAX_LAYOUT_HINTS = 12`)은 근처에도 가지 않았으므로 상한을 올려도 결과는 3으로 같다.

그 화면의 태그 분포는 `div` 195 · `td` 156 · `tr` 67 · `table` 65 · `img` 60 이고, **클래스에 `btn`/`button` 이 들어간 요소가 92개**다. 버튼이 `<button>` 이 아니라 `div` 로 만들어져 있고 레이아웃이 테이블 기반이다. 현재 셀렉터에 이 태그들이 하나도 없다.

**대조군 — 데모 페이지**(`examples/demo-site`)는 `<header>`·`<main>`·`<aside>`·`<form>`·`<button>` 으로 짜여 있어 힌트 12개가 잡힌다. 이 결함이 오래 안 걸린 이유가 이것이다. **검증 대상이 데모 페이지뿐이었고, 데모 페이지에서는 멀쩡해 보인다.**

### 원인

수집기가 **이름으로 고른다** — 태그 이름과 `role` 속성. 이름은 사이트마다 다르다. `<button>` 을 쓰는 팀, `div.btn` 을 쓰는 팀, 테이블로 레이아웃을 짜는 팀이 모두 있다. 이름에 기대는 한 다음 사이트에서 또 깨진다.

거기에 더해 `nearestContainer`(`dom.ts:269`)가 후보 범위를 클릭 지점의 가장 가까운 컨테이너로 제한한다. 데모 페이지에서 이 값이 `main` 이라 헤더·사이드바가 애초에 후보에 들지 못했다.

## 목표

- **어떤 사이트에서든** 화면을 알아볼 만큼의 구조가 담긴다 — 시맨틱 HTML 이든, `div`/테이블로 짠 화면이든.
- 지금 잘 동작하는 시맨틱 페이지에서 **나빠지지 않는다.**
- 클릭당 비용이 문서 크기와 무관하게 묶인다.
- 개인정보 노출면이 늘지 않는다.

## 목표가 아닌 것

- **클래스 이름으로 고르기.** `[class*=btn]` 같은 규칙은 지금 이 사이트에 맞추는 것이고, 클래스는 CSS 모듈·빌드 해시로 배포마다 바뀐다. 요소 신원 설계(`2026-09-03-element-identity-design.md`)가 같은 이유로 클래스를 배제했다.
- **화면을 실제로 캡처하기.** 스크린샷이나 DOM 스냅샷은 사용자 데이터를 통째로 담는다. 와이어프레임 방식은 그것을 피하려고 선택한 구조이고, 이 설계는 그 선택을 유지한다.
- **다른 출처 iframe 내부 수집.** 브라우저가 막는다(§2 실측). 정책이 아니라 물리적 제약이다.
- **중첩 iframe 재귀.** 한 겹만 내려간다. 재귀하면 비용이 예측 불가능해진다.
- **미리보기 렌더러 개선.** `ScreenContextPreview` 는 힌트를 전부 그리므로 이번 범위에서 변경이 없다.

## 1. 후보 선정 — 네 단계

싼 신호부터 쓰고 비싼 신호는 예산 안에서만 쓴다.

### ① 랜드마크 — 공짜

기존 `LANDMARK_SELECTOR` 를 그대로 둔다. `querySelectorAll` 한 번이다.

이 단계를 없애면 안 된다. 관리자 앱(`:5173`)에서 측정한 결과, "칠해짐" 판정만 쓰면 **`<main>` 과 `<header>` 를 잃는다** — 배경도 테두리도 없는 투명한 레이아웃 껍데기라 칠해짐 판정에 걸리지 않기 때문이다. 화면 골격으로는 가치가 있으므로 **교체가 아니라 합집합**이다.

| 관리자 페이지(:5173) | |
|---|---|
| 현재 방식 후보 | 14 |
| 칠해짐 방식 후보 | 53 |
| 현재 방식만 잡던 것을 잃음 | **2 (`MAIN`, `HEADER`)** |

### ② rect 스캔 — 싼 것

**`nearestContainer` 범위 제한을 없앤다.** 문서 전체를 훑되 `getBoundingClientRect` 만 읽는다. 2,360 요소 화면에서 2.3ms 로 측정됐다.

거르는 조건은 둘이다.

- 최소 크기 8×8 미만 제외 — 사람 눈에 상자가 아니다
- 뷰포트와 겹치지 않는 것 제외 — 미리보기에 그릴 수 없다

거대 문서 대비 `MAX_RECT_SCAN` 상한을 둔다.

### ③ style 판정 대상을 60개로 줄인다 — 비싼 것

②를 통과한 전부에 `getComputedStyle` 을 부르면 2,360 요소에서 13ms 다. rect 만으로 매긴 점수 상위 60개로 줄이면 0.9ms 다.

60은 기존 `MAX_HINT_CANDIDATES` 상수를 재사용한다. 뜻이 "검사 후보 상한"에서 **"`getComputedStyle` 호출 예산"** 으로 좁아진다.

60을 반으로 나눈다 — **면적 상위 30**(골격 후보) + **클릭 거리 상위 30**(근처 후보). 한쪽으로만 뽑으면 다른 쪽이 후보에조차 들지 못한다.

### ④ 칠해짐 판정과 중복 접기

넷 중 하나라도 있으면 사람 눈에 상자다.

- 배경색이 투명이 아님
- 테두리 두께가 0이 아님
- `<img>` 이거나 `background-image` 가 있음
- **직접 텍스트 노드**를 가짐 (자손이 아니라 자기 자신의 텍스트)

그다음 두 겹으로 접는다.

- rect 가 완전히 같으면 하나만 남긴다 (기존 `seen` 로직 유지)
- **부모와 rect 가 거의 같으면 자식을 버린다** (신규, 4px 이내). 래퍼 `div` 가 겹겹이 쌓인 구조에서 같은 상자를 여러 번 그리는 것을 막는다.

## 2. iframe

측정한 팝업 화면에서 **우측 본문 1056×576 이 통째로 같은 출처 iframe** 이었다. 내부에 요소 31개가 있는데 `document.querySelectorAll` 이 프레임 경계를 넘지 못해 하나도 보지 못했다. 미리보기에서 화면 절반이 빈 상자로 보이던 원인이다. 편집기·미리보기·결제 위젯은 iframe 이 흔하므로 이 앱만의 특성이 아니다.

### 실측한 경계

| | 같은 출처 | 다른 출처 |
|---|---|---|
| `contentDocument` | 접근 가능 | **`null`** |
| `contentWindow.document` | 접근 가능 | **`SecurityError` 던짐** |
| iframe 요소 자체(rect·태그) | 보임 | 보임 |

두 갈래로 막히는 것이 중요하다. 하나만 처리하면 다른 쪽에서 예외가 새어 나가고, `getScreenContext` 의 바깥 `try/catch`(`dom.ts:372`)에 걸려 **화면 맥락이 통째로 사라진다.**

### 규칙

- **같은 출처** — 한 겹 내려가 내부 상자를 수집한다. 내부 요소의 rect 는 iframe 기준이므로 **iframe 의 rect 를 더해 부모 문서 좌표로 보정한다.** 텍스트 정책은 부모 문서와 동일하게 적용한다.
- **다른 출처** — 들어가지 않되 **iframe 사각형 자체를 힌트 하나로 남긴다.** 건너뛰면 그 영역이 미리보기에서 빈 곳으로 보여 "원래 비어 있었다" 는 오해를 낳는다. 사각형을 남기면 "볼 수 없는 영역" 으로 정직하게 표시된다.
- **한 겹만** — 중첩 iframe 은 따라가지 않는다.
- 접근 시도는 `contentDocument` 의 `null` 과 `contentWindow.document` 의 예외를 **모두** 처리한다.

부수 효과로 개인정보 경계가 저절로 지켜진다. 결제 iframe 안의 카드번호 입력칸은 읽을 방법 자체가 없다 — 우리가 조심해서가 아니라 브라우저가 막아서다.

## 3. 예산 배분

`MAX_LAYOUT_HINTS` 를 12에서 **20**으로 올린다.

실측 좌표로 12·20·30 예산의 미리보기를 그려 비교한 결과, 결정적 차이는 **3 → 12** 였고 12 → 20 은 개선, 20 → 30 은 거의 무의미했다. 20을 고른 것은 12에서 이미 넘은 문턱에 여유를 두기 위해서다.

**골격 12 + 클릭 근처 8** 로 고정한다.

- **골격** — 면적 큰 순. 이미 뽑은 상자와 rect 가 거의 같으면 건너뛴다. 겹침(포함 관계)을 이유로 버리지 않는다 — 큰 상자 안을 채우는 것이 목적이므로 포함 관계로 자식을 버리면 오히려 비어 보인다.
- **클릭 근처** — 중심 거리 가까운 순. 골격으로 이미 뽑힌 것은 건너뛴다.
- **한쪽이 부족하면 다른 쪽이 채운다.** 골격 후보가 3개뿐인 단순한 화면에서 12칸을 비워 두지 않는다.

## 4. 계약·서버·페이로드

### 계약 — 한 줄

```ts
// packages/shared/src/events.ts:208
layoutHints: screenLayoutHintSchema.array().max(12)  →  .max(20)
```

`max` 를 넓히는 방향이라 기존에 저장된 12개짜리 데이터가 그대로 유효하다. 마이그레이션이 없다.

### 페이로드 — 실측

| 힌트 수 | `screenContext` | 분노 클릭 8연타 |
|---|---|---|
| 3 | 511 B | 4.0 KB |
| 12 | 1,411 B | 11.0 KB |
| **20** | **2,229 B** | **17.4 KB** |

배치 상한은 이벤트 100개(`ingestion.ts:106`)이고 `bodyLimit` 이 설정되지 않아 Fastify 기본 1MB 다. 최악(100 × 2.2KB = 220KB)에도 여유가 크다.

### 서버 — 변경 없음

`sanitizeScreenContext` 는 힌트를 개수가 아니라 하나씩 검사한다. 새로 들어올 `div`·`td` 는 `SERVER_TEXT_TAGS` 에 없어 서버가 텍스트를 한 번 더 지운다. SDK 가 실수로 글자를 실어 보내도 경계에서 걸린다. `screenLayoutHintSchema` 의 `refine`(masked 인데 텍스트가 있으면 파싱 실패)도 그대로 유효하며, 이번 변경에서 더 중요해진다.

### 관리자 렌더러 — 변경 없음

`ScreenContextPreview` 는 `layoutHints` 를 전부 그린다.

### 성능

| 단계 | 비용 (2,360 요소) |
|---|---|
| rect 스캔 | 2.3 ms |
| `getComputedStyle` 60개 | 0.9 ms |
| 합계 | **약 3 ms** |

분노 클릭 8연타에 24ms. `MAX_RECT_SCAN` 과 `MAX_HINT_CANDIDATES`(60)가 이 비용을 문서 크기와 무관하게 묶는다.

### 개인정보

노출면이 늘지 않는다. 새로 후보가 되는 `div`·`td` 는 텍스트 화이트리스트(`TEXT_TAG_WHITELIST` = `button`·`a`·`h1~h3`, `TEXT_ROLE_WHITELIST` = `button`·`link`·`tab`·`heading`)에 없어 `allowsHintText` 가 막는다. 저장되는 것은 rect 와 tagName 뿐이다.

다만 ④의 "직접 텍스트가 있으면 상자로 친다" 판정은 텍스트를 **읽는다**. 읽은 것을 저장하지 않는다는 것을 테스트로 못박는다.

## 5. 검증

이 결함이 안 걸린 이유가 검증 대상이 데모 페이지뿐이었기 때문이므로, 검증을 세 겹으로 둔다.

### 단위 테스트

기존 `dom.test.ts` 는 `stubRect` 로 요소마다 rect 를 주입하는 관례를 갖는다. `getComputedStyle` 은 jsdom 이 기본값을 주므로 배경색·테두리를 주입하는 `stubStyle` 헬퍼를 옆에 만든다.

**비시맨틱 픽스처를 새로 만든다** — `div` 만으로 짠 툴바, `table`/`td` 레이아웃, `role` 속성 없음, `<button>` 0개. 실제 제품 화면을 닮은 모양이다.

- 이 픽스처에서 힌트가 **12개 이상** 나온다 (현재 코드는 0~2개)
- 이 테스트가 회귀 방지선이다 — 누가 셀렉터 기반으로 되돌리면 여기서 걸린다

**시맨틱 페이지가 나빠지지 않는 것을 못박는다.**

- 랜드마크만 있고 아무것도 칠해지지 않은 페이지에서 랜드마크가 힌트로 남는다
- 데모 페이지 모양의 픽스처에서 힌트 수가 줄지 않는다 — "새 방식이 옛 방식의 상위집합" 을 고정한다

**iframe**

- 같은 출처: 내부 상자가 수집되고 좌표가 부모 기준으로 보정된다 (iframe 이 `x:400` 이면 내부 `x:10` 요소는 `x:410`)
- 다른 출처: `contentDocument` 가 `null` 인 경우와 `contentWindow.document` 가 던지는 경우 **양쪽 다** 조용히 건너뛰고, iframe 사각형은 힌트로 남는다

**개인정보**

- `div`·`td` 힌트에 `textMaskedOrLimited` 가 없다
- 칠해짐 판정에 쓰인 문자열이 힌트에 새어 들어가지 않는다
- 같은 출처 iframe 내부 요소에도 텍스트 화이트리스트가 동일하게 적용된다
- 생산자 출력이 `screenContextSchema` 를 항상 통과한다 (기존 `expectValidScreenContext` 관례 유지)

**비용 상한**

- `MAX_RECT_SCAN` 을 넘는 문서에서 스캔이 멈춘다
- `getComputedStyle` 호출이 60을 넘지 않는다 — 스파이로 호출 횟수를 센다

### 실측 검증 (시드 금지)

데모 페이지만으로는 이 결함을 다시 놓친다. **실제 제품 화면**에서 확인한다.

- ONEFFICE 팝업에서 클릭 → 힌트가 3개에서 12개 이상으로
- 미리보기에 좌/우 2단 구조와 상단 툴바가 드러난다
- iframe 본문 영역이 더 이상 빈 상자가 아니다
- 데모 페이지(시맨틱)도 함께 확인해 나빠지지 않았다

## 6. 성공 기준

- 비시맨틱 픽스처에서 힌트 12개 이상 (현재 0~2)
- 시맨틱 픽스처에서 힌트 수가 줄지 않음
- `getComputedStyle` 호출이 클릭당 60 이하
- 다른 출처 iframe 에서 예외가 새지 않고 사각형이 남음
- 구조 힌트(`div`·`td`)에 텍스트 0건
- SDK 번들 gzip 10KB 이내 (현재 5,197 B) — 초과하면 멈추고 보고
- 실측: 실제 제품 팝업 화면에서 화면 구조를 알아볼 수 있음
- 기준선 641 테스트 통과

## 7. 남는 한계

- **다른 출처 iframe 내부는 영원히 볼 수 없다.** 사각형으로 "볼 수 없는 영역" 임을 표시하는 것이 할 수 있는 전부다.
- **중첩 iframe 은 한 겹까지만.** 두 겹 이상 안쪽은 담기지 않는다.
- **Canvas·WebGL 로 그린 화면은 상자 하나다.** `<canvas>` 는 칠해짐 판정에 걸리지만 내부 구조는 DOM 에 없다.
- **Shadow DOM 은 이번 범위 밖이다.** `querySelectorAll` 이 shadow root 를 넘지 않는다. 웹 컴포넌트로 짠 화면은 여전히 얇게 담긴다 — 별도 작업.
- **20칸이 충분한지는 실측 후 재검토한다.** 12·20·30 비교에서 20이 합리적으로 보였으나, 화면이 훨씬 복잡한 경우는 아직 보지 않았다.
