# 세션 리플레이 — 기록과 전송

## 배경

2026-09-14 세션에서 **와이어프레임 미리보기로는 "사용자가 어떤 흐름으로 썼나" 에 도달할 수 없다**는 것이 확정됐다. 그날 하루에 다섯 방향을 시도했고 전부 같은 벽에 부딪혔다.

### 와이어프레임의 벽 (실측)

미리보기는 뷰포트를 축소해 그리는데 글꼴은 같이 줄지 않는다.

- 메뉴 항목은 뷰포트가 커져도 **48px 근처로 유지**된다. 4글자(44px)를 넣으려면 배율 **0.92** 가 필요하다 — 뷰포트 1456px 이면 미리보기가 1,339px, 2000px 이면 1,840px 이어야 한다. 대시보드 카드에 안 들어가고, **뷰포트가 클수록 나빠진다.**
- 실제 렌더 폭 18px 인 레일 상자에 들어가는 글자 수: **11px 에서 1자, 9px 에서 1자, 7px 에서 2자.** 7px 한글은 읽을 수 없고, 2글자로는 `회계관리`/`회계마감` 을 구분하지 못한다.
- 이름 있는 상자 34개 중 인라인으로 읽히는 것은 **5개**뿐이었다.
- 기각한 방향: 글꼴 축소 · 글자 수 제한 · 미리보기 확대 · callout 번호 · 컨테이너 제거(수집·렌더러 양쪽).

### 리플레이 기각을 뒤집은 근거

같은 날 오전에 로드맵 4단계를 "도입하지 않음" 으로 닫았다가 오후에 뒤집었다. 닫을 때 쓴 측정이 틀렸다 — 이벤트마다 화면 전체를 담는 비용(스크린샷 61,572 B · `outerHTML` 7.2 MB)을 재고 기각했는데, rrweb 류는 스냅샷을 **한 번** 찍고 그 뒤로는 **DOM 변경분만** 흘린다. 로드맵이 말한 기법이 아니라 허수아비를 잰 것이다.

사용자 앱(요소 2,465개)에서 실제로 기록해 다시 쟀다.

| 항목 | gzip |
|---|---|
| 초기 스냅샷 (기본 설정) | 5,622,285 B |
| CSS 링크 (`inlineStylesheet: false`) | 5,285,916 B |
| 이미지 제외 | 356,261 B |
| **CSS 링크 + 이미지 제외** | **30,016 B** |
| mutation | **209 B/s** (1분 12.6 KB · 10분 126 KB) |

스냅샷의 **95%가 base64 이미지**였다 — 145개, 큰 것은 개당 61 KB. 두 레버가 곱으로 들어 **이미지가 187배, CSS 가 12배**다.

**10분 세션 약 156 KB.** 오늘 기준 클릭 26회분이다.

## 목표

- 사용자가 막힌 세션의 **흐름을 재생**해서 볼 수 있다.
- 문제 없는 세션은 **브라우저를 떠나지 않는다.**
- 설치는 지금 그대로 **스크립트 한 줄** — `src` 와 `data-project-id` 뿐이다.
- 기본 SDK 번들은 gzip **10,240 B** 예산 안에 머문다.
- 리플레이를 켜지 않은 프로젝트는 rrweb 을 **받지 않는다.**

## 목표가 아닌 것

- **재생 UI.** 관리자 리플레이어는 하위 프로젝트 `B` 다. 다만 이 스펙의 검증 일부는 B 가 있어야 가능하다(§6).
- **와이어프레임 걷어내기.** 하위 프로젝트 `C` 다. **리플레이가 실제로 동작하는 것을 확인한 뒤** 지운다 — 먼저 지우면 되돌릴 곳이 없다.
- **서버의 마스킹 재판정.** 불가능하다. §5 에 그 대가를 적는다.
- **모든 세션 기록.** §2 의 트리거 방식이 이 스펙의 전제다.

## 1. 무엇을 기록하고 무엇을 버리는가

### rrweb 설정

```
maskAllInputs    : true
inlineStylesheet : false
recordCanvas     : false
collectFonts     : false
inlineImages     : false
slimDOM          : on
checkoutEveryNms : 120000   (§2 버퍼)
```

### 이미지는 직접 걷어낸다

이 버전의 rrweb 에는 `maskAttributeFn` 이 **없다**(번들 grep 0회). 대상 앱의 이미지는 HTML `src` 에 이미 박힌 base64 라 rrweb 이 그대로 복사한다.

스냅샷 이벤트가 JSON 노드 트리이므로 **emit 직후 우리가 순회**해서 `src`·`href`·`srcset` 의 `data:` 값을 자리표시자로 바꾼다.

리플레이에서 아이콘은 빈 상자가 된다. **흐름을 읽는 것은 배치와 글자가 하고 아이콘은 하지 않으며**, 187배를 지불할 값이 아니다.

### CSS 는 링크로 둔다

대상 앱의 스타일시트 4개가 전부 같은 출처(`/static/css/*.chunk.css`, 규칙 17,355개)라 리플레이어가 URL 로 받을 수 있다.

**대가:** 파일명에 빌드 해시가 붙어 있어(`main.ef57171d.chunk.css`) **배포가 바뀌면 과거 세션의 스타일이 깨진다.** 오래된 리플레이일수록 깨질 확률이 높고, 이는 §4 의 짧은 보존 기간과 맞물린다.

인라인하면 세션당 356 KB 로 12배가 되지만 영원히 정확하다. **링크를 기본으로 하고**, 스타일 유실이 실제 문제가 되면 그때 프로젝트별 옵션을 둔다.

### 마스킹 세 겹

```
1. 구조   maskAllInputs + 운영자 지정 셀렉터 → maskTextSelector
2. 패턴   maskTextFn 안에서 redactText — 이메일·한국 휴대폰·9자리+ 숫자
3. 경계   서버가 크기·구조를 검증 (텍스트 재판정은 불가, §5)
```

구조가 먼저다. 입력값이 패턴에 안 걸려도 이미 가려져 있다.

**정직하게 남는 구멍:** `최미애` 처럼 패턴이 없고 구조로도 안 잡히는 이름은 **운영자가 셀렉터로 지정해야** 가려진다. 2026-09-14 실측에서 `redactText` 를 통과하는 것을 확인했다. 그리고 "사용자 데이터가 들어가는 자리" 를 구조만으로 판정하는 규칙은 일반적으로 쓸 수 없다 — 대상 앱은 랜드마크 0개, 메뉴가 `span`, 버튼이 `div`, 레이아웃이 `table` 이다.

## 2. 버퍼와 트리거

### 롤링 버퍼

`checkoutEveryNms` 가 2분마다 전체 스냅샷을 다시 찍어주므로, 그보다 오래된 것을 버릴 수 있다.

**버리는 시점을 한 세대 늦춘다.** 새 체크포인트가 와도 바로 앞 스냅샷을 버리지 않고, 그 다음 체크포인트가 올 때 버린다. 그래서 실제로 메모리에 쥐고 있는 것은 **스냅샷 하나 + 그 뒤의 모든 변경분**이다.

| 방식 | 메모리 | 거슬러 보는 시간 |
|---|---|---|
| 새 체크포인트가 오면 바로 버림 | 383 + 25 = 약 **410 KB** | **0~2분 (운에 달림)** |
| **한 세대 늦춰 버림** | 383 + 50 = 약 **433 KB** | **2~4분 (보장)** |

스냅샷은 압축 전 383 KB 로 비싸지만 변경분은 209 B/s 라 4분치가 50 KB 다. **메모리 23 KB 를 더 쓰고 최소 2분을 보장**받는다. 바로 버리면 체크포인트 직후에 난 문제는 앞 맥락이 거의 0초가 되어, 같은 종류의 문제인데 어떤 건 앞이 통째로 없다.

**구현에서 먼저 확인할 것:** rrweb 이 체크포인트마다 노드 id 를 다시 매긴다면 옛 스냅샷에 새 변경분을 이어 붙일 수 없어 **스냅샷 두 벌(약 816 KB)** 을 쥐어야 한다. 그때도 설계는 같고 메모리만 바뀐다 — 표의 숫자를 실측으로 고친다.

### 트리거

```
분노 클릭       같은 요소 3초 내 3회
오류            window.onerror
반응 없는 클릭   클릭 후 2초간 mutation 0
```

트리거가 걸리면 오래된 체크포인트부터 올리고, **그 뒤로는 계속 이어서 올린다.** 문제가 난 뒤에 무슨 일이 있었는지가 종종 더 중요하다.

### SDK 트리거는 서버 탐지의 사본이 아니다

| | SDK 트리거 | 서버 탐지 |
|---|---|---|
| 질문 | "이 세션을 올릴까?" | "이게 이슈인가?" |
| 성격 | **느슨하게. 놓치는 것보다 더 올리는 게 낫다** | 정확하게 |
| 정본 | 아니다 | **이슈의 정본** |
| 틀렸을 때 | 리플레이 몇 개가 더 저장됨 | 이슈 판정이 틀림 |

세 번째 트리거가 서버 규칙과 **다르다.** 서버는 "2초 안에 같은 세션의 다른 이벤트가 없음", SDK 는 "2초 안에 DOM 변경이 없음" 이다. **같게 만들려 하지 않는다.** 이 저장소는 상수 하나를 두 벌로 갈라 뒀다가 조용히 깨진 전례가 있고(계약 20 / 수집 API 12), 규칙을 두 벌로 두면 같은 일이 반복되며 이번엔 실패가 더 조용하다 — 리플레이가 그냥 안 올라온다. 둘을 **다른 일을 하는 것으로 이름 지어** 그 함정을 피한다.

### 미정

**세션당 업로드 상한.** 한 세션에서 분노 클릭이 반복되면 계속 올라갈 수 있다. "세션당 1회 트리거, 이후엔 이어 올리기만" 이 자연스러우나 구현 중 실측으로 정한다.

## 3. 설정 — 기록 시작의 전제

SDK 가 기록을 시작하려면 두 가지를 알아야 한다.

```
GET /v1/projects/:projectId/config
    → { replay: true, maskSelectors: [".customer-name", "td.amount"] }
```

> **설정이 도착하기 전에는 기록을 시작하지 않는다.**

마스킹 셀렉터를 모르는 채로 기록하면 가려야 할 것을 원문으로 담고, 나중에 설정이 와도 이미 버퍼에 들어가 있다. **세션 앞 수백 ms 를 잃는 것과 개인정보를 원문으로 담는 것 중에는 앞을 택한다.**

이 엔드포인트는 공개다(`projectId` 가 페이지 소스에 있다). 노출되는 것은 그 사이트가 어떤 셀렉터를 가리는지이고, 그 클래스명은 이미 사이트 HTML 에 보이는 값이다.

## 4. 전송·저장·보존

### 별도 엔드포인트

```
POST /v1/sessions/:sessionId/recording
```

이벤트 배치(`/v1/events/batch`)에 태우지 않는다. 그쪽은 `MAX_BATCH_BODY_BYTES = 48 KiB` 로 묶여 있는데, 그 값은 브라우저의 `keepalive` 64 KiB 한도 때문에 2026-09-14 에 넣은 것이다(넘으면 네트워크 오류로 거절돼 배치가 큐로 되돌아가 영구히 막힌다). 성격이 다른 두 트래픽을 한 통에 넣으면 서로를 밀어낸다.

**keepalive 를 쓰지 않는다.** 평범한 `fetch` 로 보내고, `pagehide` 때 마지막 꼬리만 keepalive 로 보낸다.

### 압축

`CompressionStream("gzip")` 으로 브라우저에서 압축해 보내고 서버가 푼다. 383 KB → 30 KB (12.8배).

`bodyLimit` 은 현재 설정이 없어 Fastify 기본 1 MB 다. **이 엔드포인트에는 명시적 상한을 걸고, 압축 해제 후 크기도 함께 제한한다**(압축 폭탄 방지).

### 저장

```sql
CREATE TABLE session_recordings (
  session_id  TEXT NOT NULL,
  project_id  TEXT NOT NULL,
  seq         INTEGER NOT NULL,   -- 업로드 순번
  started_at  TEXT NOT NULL,      -- 이 청크 첫 이벤트 시각 (UTC ISO)
  bytes       BLOB NOT NULL,      -- gzip 된 rrweb 이벤트 배열
  PRIMARY KEY (session_id, seq)
);
```

세션 하나를 통짜 blob 으로 두면 이어 올릴 때마다 통째로 다시 써야 한다. 재생 시 `seq` 순으로 이어 붙인다.

### 보존

```
SESSION_RECORDING_RETENTION_DAYS   기본값 7
```

`EVENT_RETENTION_DAYS` 와 **같이 쓰지 않는다.** 이벤트 한 건이 6 KB 인데 세션 기록은 150 KB 로 25배고, **개인정보 구멍의 크기가 보존 기간에 비례**한다.

**기본값을 두는 것이 중요하다.** `EVENT_RETENTION_DAYS` 는 기본값이 없어 설정하지 않으면 영원히 쌓이는데, 리플레이에 같은 성질을 주면 안 된다. §1 에서 CSS 를 링크로 두기로 했으므로 오래된 리플레이는 어차피 스타일이 깨진다 — 길게 둘 값이 없다.

### 계약

```ts
export const recordingChunkSchema = z.object({
  sessionId: z.string().refine(isSafeTraceIdentifier),
  seq: z.number().int().min(0),
  startedAt: z.string().datetime(),
  eventCount: z.number().int().min(1),
});
```

**rrweb 이벤트 본문은 스키마로 검증하지 않는다.** 형태가 rrweb 버전에 묶여 있어 계약으로 고정하면 라이브러리를 못 올린다.

| 서버가 검증하는 것 | 서버가 하지 않는 것 |
|---|---|
| 프로젝트·세션 존재, 허용 도메인 | rrweb 이벤트 내부 구조 |
| 압축 해제 후 크기 상한 | **마스킹이 제대로 됐는지** |
| `seq` 중복·역행 | |

## 5. 잃는 것 — 경계의 방어 한 겹

이 저장소는 "서버가 SDK 를 안 믿는다" 를 지켜왔다. 힌트 텍스트를 태그로 재판정해 지우는 코드가 그 예다.

**리플레이에서는 그것이 불가능하다.** rrweb 이벤트 안의 텍스트가 마스킹됐는지 서버가 다시 판정하려면 DOM 트리를 해석해야 하고, 그건 사실상 rrweb 을 서버에 다시 구현하는 일이다.

그래서 **마스킹의 정본은 SDK 한 곳**이 된다. 2026-09-14 의 라벨 작업에서 "방어가 한 겹 줄었다" 고 적었는데, 리플레이에서는 그 겹이 **아예 없다.** 이것은 리플레이를 택하면 따라오는 대가다.

완화는 셋뿐이다 — 트리거 방식(문제 난 세션만 올라간다) · 짧은 보존 · README 의 정직한 서술.

## 6. 검증

### 단위 테스트

- 설정이 도착하기 전에는 `rrweb.record` 가 호출되지 않는다
- **트리거 전에는 아무것도 전송되지 않는다** ← 가장 중요하다
- 마스킹 셀렉터가 `maskTextSelector` 로 전달된다
- `maskTextFn` 이 `redactText` 를 거친 값을 돌려준다
- 스냅샷의 `data:` URI 가 자리표시자로 바뀐다
- 버퍼가 직전 체크포인트까지만 유지하고 그 이전은 버린다
- 트리거 셋이 각각 업로드를 촉발한다
- 리플레이를 켜지 않은 프로젝트는 `/trace-replay.js` 를 받지 않는다

### 실측

- 실제 앱에서 10분 세션 크기 (목표 약 156 KB)
- 기본 SDK 번들 gzip ≤ 10,240 B

### B 가 있어야 확인되는 것

- **리플레이가 실제로 흐름으로 읽히는가.** 숫자가 맞아도 이것이 안 되면 의미가 없다 — 와이어프레임이 정확히 여기서 실패했다.
- CSS 를 링크로 뒀을 때 관리자 화면에서 스타일이 붙는가
- 마스킹 후에도 흐름을 이해할 수 있는가 (다 가리면 리플레이가 무의미해진다)

**A 만으로는 "동작한다" 를 말할 수 없다.** A+B 를 묶어 한 번 검증한다.

## 7. 번들

```
/trace.js         기본 SDK. 항상 로드            목표 gzip ≤ 10,240 B
/trace-replay.js  rrweb 포함. 켠 프로젝트만      gzip 약 44 KB
```

**설치는 한 줄 그대로다.**

```html
<script src="http://localhost:4000/trace.js" data-project-id="proj_xxx"></script>
```

`trace.js` 가 설정을 받아 `replay: true` 면 스스로 `/trace-replay.js` 를 삽입한다. 경로는 `install.ts` 가 이미 쓰는 방식으로 유도한다 — 지금도 `document.currentScript.src` 에서 수집 엔드포인트를 만든다(`new URL("/v1/events/batch", src)`).

**CDN 을 쓰지 않는다.** self-hosted 제품이 외부 의존을 만들면 안 되고, 리플레이 스크립트가 `trace.js` 와 같은 출처에서 오므로 **고객의 CSP 에 새로 추가할 것이 없다.** CDN 이었다면 고객마다 `script-src` 에 항목을 넣어야 하고, 안 넣으면 조용히 실패한다.

## 8. 하위 프로젝트 순서

```
A. 기록·전송   ← 이 스펙
B. 재생 UI      A 와 함께 검증해야 "된다" 를 말할 수 있다
C. 걷어내기     A+B 확인 후. dom.ts 약 300줄, dom.test.ts 의 상당수,
                shared 의 screenLayoutHintSchema·MAX_SCREEN_LAYOUT_HINTS,
                ingestion 의 힌트 정제, 관리자의 힌트 렌더링
```

C 에서 **남기는 것**: 클릭 좌표 · `target` · 요소 지문 · `titleMasked` · 이슈 탐지. "무엇이 문제인가" 축은 리플레이와 무관하게 필요하다.

## 9. 남는 한계

- **마스킹 정본이 SDK 한 곳이다**(§5). 서버가 검증할 수 없다.
- **패턴 없는 개인정보는 운영자가 지정해야 가려진다.** 자동으로는 못 가른다 — `회계관리`(앱이 만든 글자)와 `최미애`(사용자 데이터)는 글자로도 구조로도 구분되지 않았다.
- **CSS 를 링크로 두므로 오래된 리플레이는 스타일이 깨진다.** 보존 기간이 그 완화책이다.
- **이미지가 빈 상자로 보인다.** 187배를 지불하지 않기로 한 결과다.
- **거슬러 볼 수 있는 시간이 2~4분이다.** 그 이전은 없다.
- **번들 44 KB 는 켠 프로젝트가 지불한다.** 기본 SDK 의 7배가 넘는다.
- **`detectLongPauses` 가 죽은 코드다** — `idle` 이벤트를 기다리는데 SDK 가 만들지 않는다. 리플레이에서는 긴 멈춤이 눈으로 보이므로, 살릴지 지울지는 `C` 에서 함께 다룬다.
